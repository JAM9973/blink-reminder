기준: 2026-11-03. 공유 대화 https://chatgpt.com/share/6ae92fee-4da8-83ee-9a67-2e734cbe9bbd 의 계획을 현재 소스와 실행 결과에 맞춰 조정했다. 이번은 계획 정리 턴이며 아래 구현을 수행한 이력이 아니다.

## 지금부터의 기준

- [빠른 연속 깜빡임 개선 계획](RAPID_BLINK_PLAN.md)의 T08-A 비교 완료. [실험 결과](검증결과/2026-11-03/T08A/후보_비교_결과.md)에서 보수형은 평소 10회 유지·빠른 8회, 기존 24개+추가 15조건 통과. 빠른 10회 목표는 미달이며 현재 앱 미적용. 다음은 T08-B 검증용 반영 검토, 이후 T08-C 새 실제 시점 자료로 확인한다.

- 카메라 → EAR → C 판정 → 최근 60초 집계 → 기본 알림 소스가 이미 있다. 처음부터 다시 만들거나 발표를 위해 기능을 지우지 않는다.
- Windows DLL 빌드·기존 자동테스트 5개는 11/3 통과했다. 후속 사용자 실행 보고·첨부 화면으로 웹캠·EAR·집계·기준 미달 기본 팝업까지 동작 확인. 실제 정확도·오탐·누락은 미측정이다.
- camera_worker.py에는 좌표·CSV·FPS·일시정지 코드, app_settings.py에는 설정 저장 코드가 있다. 현재 run.cmd → blink_app.py에는 연결되지 않아 기능 완료로 볼 수 없다.
- 이미 있는 상태 전이·연속 프레임 확인·얼굴 미검출·재알림 대기를 앞으로 새로 만든 개선이라고 발표하지 않는다.
- 최근 60초는 현재 코드상 얼굴이 보인 유효 측정 시간 기준이다. 실제 경과 시간과 구분한다.

## 비교 규칙은 수정 전에 정한다

1. 밝은 정면 조건부터 시작한다. 팀원 2명·유효 측정 60초씩 반복은 제안이다. 실제 수행 인원·횟수만 결과로 기록한다.
2. 수기와 검출 시점의 대응 허용 범위 및 일대일 대응 규칙을 측정 전에 정한다. 자연스러운 깜빡임과 의도한 동작 테스트를 구분한다.
3. 대응된 검출·오탐·누락·총횟수 오차(프로그램−수기)를 기록한다. 총횟수가 같아도 오탐과 누락이 상쇄될 수 있다. 자료 확보 후 정밀도·재현율을 계산하고 분모 0은 계산 불가로 표시한다.
4. 동일 영상 비교에는 영상 재생 입력·시각 동기화 도구가 추가로 필요하다. 현재 구현됐다고 가정하지 않는다. 동일 EAR 기록의 C 재생은 판정 로직 비교에 사용할 수 있으나 영상 인식 개선의 검증을 대신하지 못한다.
5. 기준 조정용 입력과 최종 평가용 입력을 분리한다.

## 역할과 발표 근거

과제 부분주제는 조재민=입력·인식, 김재원=C 판정·집계·알림이다. 실제 전체 구현은 조재민이 통합 진행한다. 김재원의 검토·수기 정답 작성·실험·분석은 수행한 활동으로 기록하고 과거 작성자를 추정하지 않는다.

발표는 문제·목표 → 현재 기준 버전 시연 → 실제 오류 → 수정 이유와 전후 결과 → 별도 검증·한계 → 개인 기여로 구성한다. 과거의 단계별 구현 장면을 만들지 않고 지금부터 프롬프트·diff·테스트·실험·판단·실제 커밋을 남긴다. 계획 단계명과 Git 버전은 구분하고 기존 VERSION·태그 규칙을 따른다.
