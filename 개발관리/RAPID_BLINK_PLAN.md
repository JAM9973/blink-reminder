# 짧은 재개방을 구분해 연속 깜빡임을 각각 센다

작성 기준: 2026-11-03. 사용자 요청: ‘깜빡깜빡하는걸 2회로 치는게 정확도가 높으니까 2회로 세도록 개선하는게 좋을 거 같아 계획 먼저 세워줘.’ 이번 턴은 계획만 작성한다. 앱·판정·테스트 소스와 설정은 수정하지 않고 후보 실행·추가 검증도 시작하지 않는다.

후속 진행: 사용자 ‘그러면 진행해’ 요청으로 T08-A를 완료했다. [비교 결과](검증결과/2026-11-03/T08A/후보_비교_결과.md)에서 보수형이 10/8회·시험한 회귀/반례 통과로 다음 검증 후보가 됐다. 목표 10회는 미달이며 현재 앱에는 미적용이다. 아래 내용은 단계별 계획이며 실제 수행은 STATUS·LOG의 최신 기록을 따른다.

## 목표와 현재 근거

- 사용자가 수기 10회는 빠른 두 번 5묶음, 즉 개별 감김·재개방 10회임을 확인했다. 두 주기가 실제로 관측되는 빠른 두 번은 2회 집계하는 것을 목표로 한다.
- 기존 평소 속도 기록: 수기 10회·검출 10회. 빠른 두 번 기록: 수기 10회·검출 5회. 같은 설정·소스 버전의 두 파일이다.
- 기록에서 열림 기준 0.23에 못 미친 중간 EAR과 CLOSED 유지가 확인됐다. 감김이 1프레임뿐인 문제가 전부는 아니다. 관련 데이터·해석은 [예비 비교 보고서](검증결과/2026-11-03/실제_비교/예비_비교_결과.md)에 있다.
- 관측 EAR에 재개방을 구별할 정보가 충분한지는 별도 문제다. 모든 파형을 두 번으로 나누거나 검출 횟수를 일정 배수로 늘리지 않는다. 자가수기 총횟수에만 맞춘 기준을 채택하지 않는다.
- 평소 속도의 기존 결과와 한쪽 눈 제외·긴 감김 중복 방지·무효 EAR 처리·미검출/복귀·60초 집계·알림 조건을 함께 유지한다.

## T08-A: 세 후보를 작은 범위에서 비교한다

### 1. 기준 버전과 비교 자료 고정

- 현재 C·헤더·Python 브리지·실행 앱·기록기와 설정을 소스 해시 및 별도 작업본으로 보존한다. 기존 로컬 변경·Git 이력을 유지한다.
- 비교 자료는 평소 `blink_20261103_114133_631762.csv`와 빠른 `blink_20261103_114257_575690.csv`. 입력 시각·좌우 EAR·유효성·수기 보고를 고정하고 원본을 덮어쓰지 않는다.
- 후보별 결과는 별도 경로에 보관한다. 실제 C에 현재 기록을 재생한 결과(10회/5회)를 대조 기준으로 삼는다.
- 기존 24개 테스트의 현행 기대 조건을 유지한다. 정책이 달라질 항목은 변경 이유를 먼저 명시하며 목표값을 결과에 맞춰 바꾸지 않는다.

### 2. 후보와 주의점

| 후보 | 확인할 방법 | 주의점·선택 기준 |
|---|---|---|
| A: 기존 열림·감김 기준 조정 | 문턱값·확인 조건을 제한된 범위에서 비교 | 가장 작은 변경의 대조안. 전체를 1프레임으로 낮추면 잡음이 늘 수 있고, 기준에 못 미친 중간 열림은 여전히 놓칠 수 있음 |
| B: 감김 중 상대적 상승·재하강 확인 | 양쪽 EAR의 낮은 지점 → 의미 있는 동반 상승 → 재하강을 짧은 재개방 후보로 추적 | 우선 검토할 안. 작은 출렁임과 실제 두 주기를 구분해야 하며 상승 크기·지속·좌우 일치·시간 제한의 근거 필요 |
| C: 개인의 평소 열린 값에 대한 상대 기준 | 안정적으로 열린 구간을 확보한 경우만 그 기준에 대한 재개방 비율을 사용 | A/B로 부족할 때 후속 검토. 시작부터 감김·안정적 열림 부족·기준 표류에 대한 정책이 필요하므로 이번 첫 구현에 자동 포함하지 않음 |

이번 계획에서는 새 문턱값·밀리초 상수를 확정하지 않는다. 임상 기준이나 정상 깜빡임 지속 시간으로 임의의 수치를 제시하지 않는다. 기록과 반례로 후보를 좁히고 실제 적용값·근거를 함께 남긴다.

### 3. 우선 검토할 B의 상태 처리

1. 안정적 OPEN 뒤 양쪽 감김이 확인되면 첫 감김을 시작한다.
2. 감긴 구간에서 좌우 EAR이 충분히 함께 상승하면 ‘짧은 재개방 후보’로 임시 보관한다. 작은 상승 하나만으로 바로 횟수를 더하지 않는다.
3. 이후 뚜렷한 두 번째 감김이 확인되면 두 주기일 가능성을 판단한다. 일반적인 완전 재개방 경로와 중복 집계하지 않도록 한다.
4. 상승 후 재감김 없이 완전히 열린 경우는 기존 한 번의 깜빡임 경로로 처리한다. 같은 사건을 임시 경로와 최종 열림에서 두 번 세지 않는다.
5. 얼굴 미검출·무효 EAR·긴 입력 공백이 끼면 임시 재개방 정보도 버린다. 이전 정상 기록은 보존한다.

확정 시점이 늦어질 수 있으므로 ‘사건 발생 시각’과 ‘결정 시각’을 구분할 필요를 검토한다. 기존 blink 반환값(0/1)·최근 60초 배열·알림의 일관성을 먼저 설계한다. 한 입력에서 두 사건이 뒤늦게 확정되는 문제를 처리하지 않은 채 횟수만 추가하지 않는다. 공개 입출력 유지가 우선이며 변경이 필요하면 C 헤더·ctypes·CSV·재생 도구를 함께 수정·검증한다.

### 4. 먼저 넣을 회귀·반례

| 입력 | 목표 |
|---|---|
| 뚜렷한 양쪽 감김 → 짧은 재개방 → 재감김 → 열림 | 두 사건을 중복 없이 2회 |
| 한 번 감고 열기 | 1회 |
| 한 번 길게 감은 동안 EAR이 일정함 | 감긴 동안 추가 집계 없음, 정상 열림 때 기존 정책대로 1회 |

| 한쪽 눈만 반복 감기·한쪽만 상승 | 양쪽 깜빡임으로 세지 않음 |
| 임시 재개방 후보 뒤 미검출·NaN·공백 | 임시 사건 연결 금지, 기존 무효 입력 정책 유지 |
| 완전 재개방 경로와 부분 재개방 경로가 같은 사건을 가리킴 | 중복 집계 없음 |
| 연속 세 번 이상 | 각 사건을 한 번씩 세고 두 번 전용 보정에 한정하지 않음 |
| 여러 합성 입력 간격·불규칙한 간격 | 시간 조건·샘플 수 조건이 어떻게 달라지는지 확인. 실제 FPS 측정과 구분 |
| 60초 만료·기준 미달·재알림 경계 | 새 확정 시점 정책에도 배열·알림이 일관되게 동작 |

이 반례는 구현 전 검증 기준으로 작성한다. 아직 생성·실행·통과한 테스트가 아니다. 실제 기록에서 구분하기 어려운 잡음과 두 동작의 파형이 같다면, 수치만으로 해결됐다고 주장하지 않고 더 나은 입력 또는 시점 자료가 필요한 것으로 남긴다.

### 5. 후보 채택 조건

- 기존 평소 기록은 10회가 유지돼야 한다. 빠른 기록은 수기 10회와의 차이가 줄고, 2회로 나눈 구간마다 파형·시각 근거를 제시해야 한다. 목표는 10회지만 총합 10만 맞는 것으로 성공을 확정하지 않는다.
- 기존 정상·무효·집계·알림 테스트를 유지하고 위 추가 반례에서 새 오집계를 만들지 않아야 한다.
- 다른 방법이 비슷한 결과라면 변경이 작고 조건·실패 사례를 설명할 수 있는 안을 선택한다.
- 두 파일은 조정용 자료다. 후보가 여기서 목표를 만족해도 개선 완료가 아니라 T08-B 구현·T08-C 독립 확인 대상이다.
- 잡음/긴 감김의 오집계가 늘거나 관측 정보가 부족하면 기본 앱에 적용하지 않는다. 실패 후보와 이유를 기록하고 필요한 다음 입력을 구체적으로 정한다.

## T08-B: 실제 엔진에 반영하고 전달한다

- 깜빡임 판정·집계·알림의 책임은 C에 둔다. Python에 별도 깜빡임 보정기를 붙여 C 결과와 다른 숫자를 표시하지 않는다.
- 현재 CSV 설정·소스 해시·개별 blink 이벤트로 동작을 추적할 수 있게 유지한다. 새 설정·판정 사유·사건 시각이 필요하면 로그 스키마 버전과 분석 도구를 함께 관리한다.
- 기존 UI·좌표·CSV·단축키·마우스 종료를 유지한다. 앱을 실행 중인 Windows에서는 DLL 잠금에 유의해 변경 버전은 앱 종료 후 적용한다. 사용자 프로세스를 임의 종료하지 않는다.
- WSL을 사용할 수 있으면 환경·아키텍처를 확인하고 Linux 별도 빌드로 검증한다. 접근 실패면 Windows 결과만 기록하고 Linux 미검증을 유지한다.
- 기존 자료·버전을 보존하고 로컬 커밋 시 VERSION·vNN 규칙을 따른다. 코드에 없는 과거 개선 이력을 만들지 않는다.

## T08-C: 사용자에게 요청할 짧은 독립 실험

후보와 실제 구현의 자동 검증이 끝난 뒤에만 새 실험을 요청한다. 지금 사용자가 추가로 실행할 것은 없다.

1. 현재 두 파일을 다시 찍는 것으로 조정에 사용하지 않고, 새 세션에서 평소 속도와 빠른 두 번을 각각 반복한다. 각 2회 정도의 새 실행을 시작 규모로 제안하며 실제 수행 횟수만 보고한다.
2. 세션별 실제 횟수·동작 구간을 기록하고, 가능하면 짧은 영상 또는 관찰자의 시점 기록을 함께 사용한다. 앱이 얼굴 영상을 자동 저장하는 기능을 이번 범위에 추가하지 않는다.
3. 긴 감김과 한쪽 눈 동작도 확인해 새 중복 집계가 생기지 않는지 본다. 실험 전 각 동작의 기대 집계와 대응 규칙을 정한다.
4. 같은 짧은 재개방이 실제로 두 동작인지 대응할 자료가 있어야 사건별 오탐·누락을 산출한다. 자가수기 총횟수만 있으면 총차이까지만 보고한다.
5. 새 입력에서 악화되면 원래 판정으로 돌아갈 수 있게 보존하고 한계를 기록한다. 통과하면 개선 전후 사례와 별도 검증 결과를 발표 자료로 정리한다.

완료 보고는 ‘바꾼 규칙 → 같은 입력의 전후 차이 → 잡음/일상 입력의 부작용 확인 → 새 실제 입력 결과 → 남은 한계’ 순서로 작성한다. 정확도가 높아졌다는 결론은 독립 결과를 확인한 뒤 표현한다.
