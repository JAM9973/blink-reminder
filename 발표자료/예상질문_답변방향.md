# 눈 깜빡임 알림 프로그램 예상 질문과 답변 방향

제안서 발표 후 질의응답을 준비하기 위한 자료입니다. 답변은 먼저 결론을 말하고, 이유를 설명한 뒤 필요한 경우 검증 방법을 덧붙입니다. 아직 측정하지 않은 정확도나 자원 사용량은 숫자를 만들어 답하지 않습니다.

## 교수님 질문

### 1. C언어 수업인데 Python과 MediaPipe를 사용하는 이유는 무엇인가요?

**답변 방향:** 영상 입력과 눈 좌표 추출에는 기존 도구를 사용하고, C에서 직접 구현하는 판정 로직을 구체적으로 설명합니다. C가 더 빠르다는 주장은 측정 전에는 하지 않습니다.

**말할 문장:** “Python과 MediaPipe는 웹캠에서 눈 좌표를 얻고 눈의 열린 정도를 계산하는 데 사용합니다. C에서는 눈 상태 변화, 깜빡임 횟수, 최근 60초 기록과 알림 조건을 직접 구현해 수업에서 배운 내용을 적용합니다.”

**추가 질문 대비:** 상태 변수와 조건문으로 감김과 열림을 판정하고, 배열에 깜빡임 발생 시각을 저장하며, 반복문으로 오래된 기록을 제거합니다. Python에서는 ctypes로 C 라이브러리를 호출합니다. C의 입력은 양쪽 눈 EAR, 얼굴 검출 여부, 시각이고 출력은 깜빡임 여부, 집계 횟수, 알림 여부입니다.

### 2. 라이브러리를 사용하면 팀이 직접 개발하는 부분은 무엇인가요?

**답변 방향:** 외부 모델의 기능과 팀의 기능을 정확히 구분합니다.

**말할 문장:** “얼굴과 눈 좌표를 찾는 모델은 기존 MediaPipe 모델을 사용합니다. 추출한 값으로 깜빡임을 세는 규칙과 시간 집계, 알림 조건을 구현하고 UI와 연결하는 부분이 저희가 개발할 내용입니다.”

### 3. EAR은 무엇이고 어떻게 눈을 감았는지 판단하나요?

**답변 방향:** 눈의 세로 길이가 감길 때 작아지는 원리를 설명합니다. 사람마다 같은 문턱값이 최적이라는 주장은 하지 않습니다.

**말할 문장:** “EAR은 눈의 가로 길이에 대한 세로 길이의 비율입니다. 눈을 감으면 이 비율이 작아지므로 감김을 판단할 수 있습니다. 열림과 감김 기준을 따로 두고 중간 구간에서는 상태를 바로 바꾸지 않아 값이 흔들릴 때의 오류를 줄이겠습니다.”

**현재 코드의 계산식:** EAR = (세로 거리 1 + 세로 거리 2) / (2 × 가로 거리). 개인별 기준 조정은 검토할 수 있지만 자동 보정 기능이 이미 완성됐다고 말하지 않습니다.

### 4. 60초에 12회라는 기준의 근거는 무엇인가요?

**답변 방향:** 슬라이드에 표시한 사용자 설정 예시라는 점을 먼저 말합니다. 60초도 집계 단위 선택이며 의학적으로 최적이라고 단정하지 않습니다.

**말할 문장:** “12회는 알림 동작을 설명하기 위한 설정 예시이며 사용자가 바꿀 수 있습니다. 60초는 횟수를 이해하기 쉬운 집계 단위로 선택했습니다. 의학적 정상 기준이나 최적의 시간이라고 주장하는 것은 아니며, 사용 테스트를 통해 조정하겠습니다.”

### 5. 같은 상태를 두 프레임 확인하면 충분한가요?

**답변 방향:** 순간적인 오류를 줄이려는 초기 설정이라고 설명하고, 빠른 깜빡임을 놓칠 수 있다는 한계를 인정합니다.

**말할 문장:** “한 프레임에서만 발생한 인식 오류를 바로 깜빡임으로 세지 않기 위한 초기 조건입니다. 다만 처리 속도가 낮거나 깜빡임이 빠르면 놓칠 수 있으므로 실제 프레임 속도와 수기 기록을 비교해 연속 프레임 수나 시간 조건을 조정하겠습니다.”

### 6. 얼굴이 안 보이면 깜빡이지 않았다고 판단하나요?

**답변 방향:** 미검출과 깜빡임 부족을 구분합니다. 현재 코드에서는 얼굴이 검출되는 동안의 누적 측정 시간을 사용합니다.

**말할 문장:** “얼굴이 보이지 않는 시간은 깜빡임이 부족한 시간으로 계산하지 않습니다. 측정 시간을 멈추고 얼굴이 다시 보이면 판정을 재개합니다. 따라서 현재 방식의 60초는 얼굴이 보인 누적 측정 시간이며, 실제 시계의 60초와 달라질 수 있습니다.”

**추가 질문 대비:** 자리를 오래 비웠을 때 과거 기록을 유지할지 초기화할지는 추가로 정할 정책입니다. 현재 코드가 이미 긴 이탈 후 기록을 자동 초기화한다고 말하지 않습니다.

### 7. 정확도를 어떻게 검증하나요?

**답변 방향:** 같은 측정 구간의 수기 기록과 비교합니다. 총횟수 일치만으로 정확도를 입증하지 않습니다.

**말할 문장:** “같은 구간에서 사람이 센 횟수와 프로그램 횟수를 비교하겠습니다. 전체 횟수뿐 아니라 실제 깜빡인 시점도 대조해 잘못 센 경우와 놓친 경우를 따로 확인하고, 조명과 카메라 각도 등의 조건별 결과를 기록하겠습니다.”

**주의:** 얼굴 미검출 시간을 제외하는 설정에서는 양쪽 기록도 같은 유효 측정 구간을 비교해야 합니다. 검증용 녹화가 필요하다면 동의와 보관 범위를 정하고, 평소 프로그램의 영상 미저장 설계와 구분합니다.

### 8. 정확도가 몇 퍼센트인가요? 성능 목표는 무엇인가요?

**답변 방향:** 실제 촬영 비교 결과는 아직 자료에 없습니다. C 로직용 가상 입력 테스트와 실제 카메라 정확도 검증을 구분합니다.

**말할 문장:** “현재 자료에는 실제 사용자 비교 실험으로 확정한 정확도 수치가 없습니다. 우선 정상적인 깜빡임과 순간 오류, 얼굴 미검출 상황을 확인하고, 조건별 누락과 오탐을 측정해 개선하겠습니다.”

### 9. 실제로 안구건조를 예방할 수 있다는 근거가 있나요?

**답변 방향:** 개발 동기의 근거와 프로그램 효과 검증을 구분합니다.

**말할 문장:** “화면 사용과 눈의 건조감에 관한 자료를 개발 동기의 근거로 참고했습니다. 이 프로그램의 예방이나 치료 효과는 검증하지 않았으며, 이번 프로젝트에서는 깜빡임을 감지하고 사용자가 알아차리도록 알리는 기능을 목표로 합니다.”

**출처:** 미국 국립안연구소의 [Dry Eye 안내](https://www.nei.nih.gov/eye-health-information/eye-conditions-and-diseases/dry-eye)는 화면을 오래 보는 상황과 안구건조의 관련성, 화면 사용 중 휴식을 설명합니다. 이 프로그램 자체의 효과를 입증하는 자료는 아닙니다.

### 10. 백그라운드에서 카메라를 계속 쓰면 노트북이 느려지지 않나요?

**답변 방향:** 창을 숨겨도 영상 처리는 계속된다는 점과 측정 계획을 설명합니다.

**말할 문장:** “백그라운드에서도 카메라와 영상 분석을 사용하므로 자원 소모는 생깁니다. CPU와 메모리 사용량, 처리 프레임 속도와 배터리 부담을 확인하겠습니다. 해상도나 처리 빈도를 낮출 때는 빠른 깜빡임을 놓치지 않는지도 함께 검증하겠습니다.”

### 11. 현재 어디까지 구현됐고, 화면에 나온 UI가 실제 제품인가요?

**답변 방향:** 영상 4페이지에는 UI 설계안이라고 표시돼 있습니다. 실제 코드에 있는 기능을 숨기거나, 계획인 기능을 완료했다고 말하지 않습니다.

**말할 문장:** “영상에 나온 설정 화면은 설계안입니다. 현재 코드에는 눈 좌표를 추출해 C 판정 로직과 연결하는 기본 시제품이 있고, 트레이 실행과 반투명 아이콘, 사용자 설정 화면은 앞으로 보완할 부분입니다. 실제 환경의 정확도도 별도로 검증하겠습니다.”

### 12. 일정이 부족하면 어떤 기능부터 완성하나요?

**답변 방향:** 핵심 기능과 검증의 우선순위를 말합니다.

**말할 문장:** “먼저 웹캠 입력과 C 깜빡임 판정, 횟수 집계와 알림을 연결하겠습니다. 이 흐름을 검증한 뒤 백그라운드 UI를 붙이고, 꾸미기 기능보다 오류 처리와 사용자가 일시정지·종료할 수 있는 기능을 우선하겠습니다.”

**팀 역할을 물으면:** 발표 담당 구간과 실제 개발 담당은 다를 수 있습니다. 실제로 합의한 담당을 말하고, 자료만 보고 특정 팀원의 개발 역할을 만들어 답하지 않습니다.

## 다른 조 질문

### 13. 안경을 쓰거나 어두운 곳에서도 잘 되나요?

**말할 문장:** “안경 반사나 어두운 조명 때문에 눈 좌표가 불안정해질 수 있습니다. 아직 모든 조건에서 잘 된다고 보장할 수는 없으며, 안경 착용 여부와 밝기, 얼굴 각도를 바꿔 비교하겠습니다. 검출되지 않는 상황은 깜빡임 부족과 구분해 안내할 계획입니다.”

### 14. 눈을 오래 감거나 한쪽 눈만 감으면 여러 번 세나요?

**말할 문장:** “감은 상태가 유지되는 동안에는 횟수를 늘리지 않고, 감았다 다시 뜨는 상태 변화를 한 번으로 셉니다. 현재 방식은 양쪽 눈이 함께 감기고 열릴 때 판정하므로 한쪽 눈만 감는 동작은 제외합니다.”

**추가 질문 대비:** 오래 감았다 뜨는 동작도 한 번으로 셀 수 있습니다. 감긴 시간만으로 졸음을 구분하는 기능은 현재 판정에 포함되지 않습니다.

### 15. 그냥 일정 시간마다 쉬라고 알리는 타이머와 무엇이 다른가요?

**말할 문장:** “타이머는 정해진 시간이 지나면 알리지만, 저희 프로그램은 측정한 깜빡임 횟수가 설정 기준보다 낮은 상태가 이어질 때 알립니다. 실제 눈 상태를 반영하는 점이 특징이며, 타이머보다 더 효과적인지는 사용 테스트가 필요합니다.”

### 16. 알림이 계속 떠서 공부나 게임을 방해하지 않나요?

**말할 문장:** “기준 미달이 일정 시간 유지될 때만 잠깐 표시하고, 반복 알림 사이에도 대기 시간을 두겠습니다. 크기와 투명도를 조절하고 일시정지할 수 있게 설계하며, 실제로 잘 보이면서도 작업을 방해하지 않는지 확인하겠습니다.”

**추가 질문 대비:** 영상의 기준 미달 10초, 재알림 간격 60초는 설정 예시입니다. 현재 C 코드의 시간은 얼굴이 검출되는 누적 측정 시간을 기준으로 합니다. 아이콘을 너무 투명하게 만들어 알림을 못 알아보는지도 확인해야 합니다.

### 17. 카메라 영상이 저장되거나 인터넷으로 전송되나요?

**말할 문장:** “일상적인 측정에서는 영상을 저장하지 않고 노트북 안에서 처리하는 방향입니다. 현재 코드는 처음에 얼굴 모델을 내려받을 수 있지만, 카메라 영상을 서버로 보내는 기능은 없습니다. 종료할 때 카메라를 해제하고 일시정지와 사용 상태 표시도 보완하겠습니다.”

### 18. 여러 사람이 보이거나 화상회의 앱을 같이 켜면 어떻게 되나요?

**말할 문장:** “현재 시제품은 노트북 사용자 한 명을 대상으로 합니다. 여러 사람 중 누구를 측정할지 지정하는 기능은 아직 없고, 다른 앱과 카메라를 함께 사용할 수 있는지도 환경에 따라 확인이 필요합니다. 카메라를 사용할 수 없을 때는 오류를 안내하는 방향으로 준비하겠습니다.”

## 모르는 질문에 대한 대응

### 기본 순서

1. 잠깐 생각한 뒤 질문의 핵심을 확인합니다. 질문이 명확하면 다시 묻지 않아도 됩니다.
2. 알고 있는 내용부터 한두 문장으로 답합니다.
3. 확인하지 않은 부분은 범위를 정확히 말합니다.
4. 어떤 실험이나 자료로 확인할지 구체적으로 제시합니다.

**기본 문장:** “현재 설계에서는 ○○ 방식으로 처리합니다. 다만 질문하신 △△ 조건은 아직 확인하지 못했습니다. 해당 조건에서 수기 기록과 프로그램 결과를 비교해 검증하겠습니다.”

### 수치나 성능을 물었는데 모를 때

“아직 해당 조건의 결과를 측정하지 않아 수치로 답하기는 어렵습니다. 같은 조건에서 수기 기록과 프로그램 결과를 비교해 오탐과 누락을 확인하겠습니다.”

### 모르는 기술 용어나 내부 원리를 물을 때

“그 부분은 정확히 설명할 만큼 확인하지 못했습니다. 제가 이해한 범위에서는 저희가 ○○ 결과를 입력으로 사용합니다. 세부 원리는 공식 문서를 확인해 보완하겠습니다.”

**주의:** 실제로 아는 범위만 말합니다. 모델 내부 구조나 학습 방식, 성능 수치를 즉석에서 추측하지 않습니다.

### 좋은 지적을 받았을 때

“말씀하신 조건에서는 현재 방식으로 누락이 생길 수 있습니다. 그 조건을 검증 항목에 추가하고, 기준을 조정했을 때 결과가 개선되는지 확인하겠습니다.”

### 팀원이 더 잘 아는 부분일 때

“이 부분은 해당 기능을 맡은 팀원이 더 구체적으로 설명하겠습니다.”

실제 담당자가 알고 있을 때만 연결하고, 갑자기 떠넘기지 않도록 서로 핵심 답변을 연습합니다.

### 발표 범위를 넘어서는 질문일 때

“이번 프로젝트에서는 ○○까지를 목표로 정했습니다. 질문하신 △△ 기능은 추가 설계와 검증이 필요한 확장 방향으로 생각하고 있습니다.”
